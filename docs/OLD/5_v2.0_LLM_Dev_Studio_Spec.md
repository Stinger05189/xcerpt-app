# Xcerpt v2.0.0 Specification: LLM Dev Session & Diff Merge Studio

> **Document Version:** 2.0.0-SPEC

> **Target Release:** v2.0.0

---

## 1. Executive Summary & Vision Statement

Xcerpt v2.0.0 completes the transformation of Xcerpt from a unidirectional context-staging utility into a **comprehensive, bidirectional AI Development Studio**.

While v1.6 perfected the outbound context curation pipeline, v2.0 delivers the inbound response engineering suite: developers paste structured LLM generation packets directly into Xcerpt, inspect extracted file actions (`[NEW]`, `[MODIFIED]`, `[DELETED]`) in a side-by-side Monaco Diff Merge Editor, evaluate co-located architectural reasoning, and selectively merge changes into their workspace backed by micro-checkpoints and non-invasive Git safety mechanics.

```

│                                 XCERPT v2.0 BIDIRECTIONAL LOOP                         │
├──────────────────────────────────────────┬─────────────────────────────────────────────┤
│         OUTBOUND CONTEXT STAGING         │           INBOUND DEV SESSION STUDIO        │
│  - Multi-Root Scoped Tree Curation       │  - Off-Thread Fault-Tolerant Response Parser│
│  - Monaco Skip-Block Context Compression │  - File Action Manifest ([NEW/MOD/DEL])     │
│  - JIT Virtual Payload Engine            │  - Side-by-Side Monaco Diff & Hunk Merging  │
│  - Export Manifest with Embedded Skill   │  - Co-Located Reasoning & Pre-Code Drawer   │
│  - Native OS Drag & Clipboard Output     │  - Checkpoint Engine & Git Rollback Safety  │
```

## 2. Subsystem 1: Dev Session Domain Architecture & State Machine

### 2.1. Domain Entities (`src/types/session.ts`)

```typescript
export type FileActionType = "NEW" | "MODIFIED" | "DELETED" | "PARTIAL_DIFF";
export type ActionReviewStatus = "PENDING" | "REVIEWED" | "MERGED" | "REJECTED";

export interface DiffHunk {

	originalLineCount: number;

}

export interface DevSession {
	id: string;

	rawMarkdown: string;
	summary: {
		architecturalIntent: string;

		actionsCount: Record<FileActionType, number>;

		id: string;

	};
}
```

## 3. Subsystem 2: Fault-Tolerant Protocol-Compliant Parsing Engine

The response parser processes LLM Markdown outputs adhering to `Skill_code_generation_protocol.md` while providing automated heuristics to recover from imperfect model formatting.

### 3.1. Parsing Pipeline Overview

```
                         Incoming Raw LLM Response
                                     │
                                     ▼
                        CRLF Normalization (\r\n -> \n)
                                     │
                        Line-by-Line Stateful Scanner
                                     │
        ┌────────────────────────────┴────────────────────────────┐
        ▼                                                         ▼
 [Prose & Section Scanner]                                [Code Fence Engine]
 - Captures architectural intent                          - Depth-aware fence matching
 - Associates sections with file IDs                      - Missing fence auto-repair
                                                                  │
                                                                  ▼
                                                      [Action & Path Extraction]
                                                      - Strategy 1: Protocol Line 1 Tag
                                                      - Strategy 2: Fence Info-String
                                                      - Strategy 3: Comment Header
                                                      - Strategy 4: Inferred from Disk
                                                                  │
                                                                  ▼
                                                      [File Action Construction]
                                                      - Match with Local Disk Files
                                                      - Detect Skip Blocks
                                                      - Generate Diff Hunks
```

### 3.2. Bug Resolutions from Previous Prototypes

The v2.0 parser explicitly resolves the bugs identified in `llm-response-studio`:

1. **Nested Backticks (BUG-02 Resolved):**
   The parser counts opening backticks. If an outer fence begins with ` ````markdown `, it requires a matching 4-backtick sequence (` ```` `) to close. Inner 3-backtick blocks (` ```bash `) do not terminate the file buffer.
2. **Extension-Preserving Deduplication (BUG-01 Resolved):**
   If an LLM restates a file in multiple parts, duplicate filenames insert numeric suffixes _before_ the file extension (e.g., `src/App.Part2.tsx` instead of `src/App.tsx (Part 2)`), preserving syntax highlighters.
3. **Multi-File Section Association (BUG-03 Resolved):**
   Sections store an array `associatedActionIds: string[]`. When a single markdown section introduces multiple code blocks, the explanatory text remains bound to every generated file action.
4. **Platform Line Endings (BUG-04 Resolved):**
   All line feeds are normalized to `\n` on ingestion, ensuring metrics and Monaco offsets match across Windows, macOS, and Linux.

### 3.3. Fault-Tolerant Heuristic Recovery

To handle models that omit opening or closing fences:

- **Unclosed Code Fences:**
  If EOF or a new primary header (`# [WORK PACKET]`, `## Architectural Intent`) is encountered while `inCodeBlock === true`, the parser automatically flushes the buffered lines, closes the fence, and appends a notice: `parseWarnings.push("Auto-closed unterminated code fence at EOF/Header boundary.")`.
- **Naked Code Streams (Missing Opening Fence):**
  If a file path header is followed immediately by lines of recognized programming syntax without an opening fence, the engine synthesizes the opening boundary and flags the action for user review.

### 3.4. Action Extraction Fallbacks

When an LLM omits the standard Line 1 action comment (`// [NEW]`, `// [MODIFIED]`, `// [DELETED]`):

```typescript
function inferActionType(
	targetPath: string,
	workspaceFiles: Record<string, FileNode>,
): FileActionType {
	const fileExistsOnDisk = Boolean(workspaceFiles[targetPath]);

	if (!fileExistsOnDisk) {
		return "NEW";
	}

	// File exists on disk
	return "MODIFIED";
}
```

If an action is inferred without explicit protocol tags, the action card displays an informational badge: `Inferred [MODIFIED] — Missing Line 1 Protocol Comment`.

### 3.5. Protocol Scaffolding & Action Header Stripping Engine

To prevent protocol syntax from polluting the user's codebase or creating artificial diff conflicts in the editor, all transient parser headers must be stripped immediately upon extraction.

#### 1. The Purity Invariant

- **`rawPayloadContent`**: Retains the verbatim code block extracted from the markdown stream (including Line 1 action comments and path strings) strictly for debugging and diagnostic auditing.
- **`proposedContent`**: The sanitized code payload used for Monaco Diff comparison and physical disk writing. **All protocol action comments must be purged.**

#### 2. Multi-Syntax Header Stripping Patterns

The stripping engine evaluates the first non-empty line of every extracted code buffer against language-specific protocol comment patterns:

```typescript
const PROTOCOL_HEADER_PATTERNS = [
	// C-Style / Java / TS / JS / Go / Rust / C#
	/^\s*\/\/\s*\[(NEW|MODIFIED|DELETED|PARTIAL_DIFF)\]\s+[^\r\n]+/i,
	// Python / Bash / YAML / Ruby / Dockerfile
	/^\s*#\s*\[(NEW|MODIFIED|DELETED|PARTIAL_DIFF)\]\s+[^\r\n]+/i,
	// HTML / XML / Markdown
	/^\s*<!--\s*\[(NEW|MODIFIED|DELETED|PARTIAL_DIFF)\]\s+.*-->/i,
	// SQL / Lua / Ada
	/^\s*--\s*\[(NEW|MODIFIED|DELETED|PARTIAL_DIFF)\]\s+[^\r\n]+/i,
];

export function stripProtocolScaffolding(rawCode: string): string {
	const lines = rawCode.split("\n");
	if (lines.length === 0) return rawCode;

	// Locate first non-whitespace line
	const firstNonEmptyIndex = lines.findIndex((l) => l.trim().length > 0);
	if (firstNonEmptyIndex === -1) return rawCode;

	const candidateLine = lines[firstNonEmptyIndex];
	const matchesProtocolHeader = PROTOCOL_HEADER_PATTERNS.some((pattern) =>
		pattern.test(candidateLine),
	);

	if (matchesProtocolHeader) {
		// Remove the protocol comment line
		lines.splice(firstNonEmptyIndex, 1);

		// If an extraneous single blank line remains at the top, prune it to maintain clean indentation
		if (lines[firstNonEmptyIndex]?.trim() === "") {
			lines.splice(firstNonEmptyIndex, 1);
		}
	}

	return lines.join("\n");
}
```

#### 3. Diff Engine Impact

Because `proposedContent` is sanitized before it enters Monaco:

- The diff editor will **never** display Line 1 red/green conflict blocks caused by `// [MODIFIED] path/to/file.ts`.
- The developer reviews only true syntactic and functional code modifications.
- Accepting a file or merging a hunk writes 100% clean, native source code to disk.

## 4. Subsystem 3: Monaco Side-by-Side Diff Merge Studio

### 4.1. Layout & Composition

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ XCERPT DEV SESSION: Feature/Auth-Rotation                      [Revert] [Accept All]   │
├─────────────────────┬──────────────────────────────────────────────────────────────────┤
│ FILE ACTIONS        │ ARCHITECTURAL INTENT: Auth Pipeline Migration                    │
│                     │ "Migrating symmetric JWTs to asymmetric RS256 token rotation..."  │
│ [MOD] auth.ts    ✓  ├────────────────────────────────┬─────────────────────────────────┤
│ [NEW] refresh.ts    │ PROPOSED (LLM Generation)      │ CURRENT DISK FILE               │
│ [DEL] basic.ts      │ 12  import { jwt } ...         │ 12  import { jwt } ...          │
│                     │ 13+ export const rotate = () =>│ 13- export const legacy = () => │
│                     │ 14+   // ... [Skipped: 40L] ...│ 14  // ...                      │
│                     ├────────────────────────────────┴─────────────────────────────────┤
│                     │ [Merge Hunk 1] [Accept Proposed File] [Reject] [Accept & Next]   │
└─────────────────────┴──────────────────────────────────────────────────────────────────┘
```

### 4.2. Monaco Diff Editor Wiring

- **Left Pane (Modified/Incoming):** Displays `proposedContent` (the sanitized, header-stripped LLM generation). Read-only by default, editable on toggle.
- **Right Pane (Original/Disk):** Displays the active workspace file loaded directly from disk. **Fully editable.**
- **Hunk Merging:**
  - Monaco Diff decorations expose inline merge buttons adjacent to change blocks.
  - Clicking `[Merge Hunk]` writes that specific modification into the right-hand file buffer without applying subsequent unreviewed hunks.
- **Dedicated Mode for `[NEW]` Actions:**
  - Bypasses diff comparison; renders a single editor pane showing the sanitized new file contents (`proposedContent`) with syntax highlighting and a primary `[Create File on Disk]` action.
- **Dedicated Mode for `[DELETED]` Actions:**
  - Renders a red-tinted tombstone banner displaying the file to be removed, file statistics, and a primary `[Confirm File Deletion]` action.

### 4.3. Skip Block Transparency Rule

**[IMMUTABLE DIRECTIVE] Xcerpt strictly prohibits synthesizing artificial code to hide skip blocks.**

- If the LLM output contains `// ... [Skipped: 140 lines] ...`, the skip marker is rendered directly in the diff stream.
- Monaco line decorations tint the skip marker in amber with an icon indicating skipped lines.
- This empowers the human developer to discern whether the LLM legitimately skipped irrelevant code or accidentally omitted critical logic before merging.

### 4.4. Auto-Advance Review Engine

When a user clicks `[Accept Proposed File]`, `[Create File]`, or `[Confirm Deletion]`:

1. Physical disk write / deletion executes immediately.
2. The action's `reviewStatus` updates to `'MERGED'`.
3. The left sidebar checklist checks off the item.
4. The studio **automatically loads the next unreviewed file action**, delivering a streamlined review workflow.

## 5. Subsystem 4: Co-Located Explanation & Reasoning Drawer

### 5.1. Contextual Reasoning Co-Location

One of the most significant cognitive burdens in AI code review is switching between chat windows to re-read explanations while reviewing diffs.

Xcerpt v2.0 solves this by parsing markdown explanations that precede code blocks and rendering them in an integrated **Reasoning Drawer** directly above the diff editor:

- **Pre-Code Summary:** Displays the architectural intent and file manifest.
- **Inline Explanations:** Displays rationale specific to the active file.
- **Collapsible Layout:** Can be expanded to review complex logic or collapsed to maximize diff editor space.

## 6. Subsystem 5: Checkpoint Engine & Non-Invasive Git Safety

### 6.1. Ephemeral Pre-Session Checkpoints

Before any file write is permitted in a Dev Session, Xcerpt creates a **Session Checkpoint**:

1. **In-Memory Snapshot:** Captures the verbatim original text of every file targeted by the session actions.
2. **Disk-Backed Session State:** Writes the snapshot to `XcerptSessions/<workspaceId>/sessions/<sessionId>.json`.
3. **Session Reversion:** Clicking `[Revert Session]` restores all merged files back to their exact pre-session snapshot states instantly, completely independent of external Git state.

### 6.2. Non-Invasive Git Working Tree Integration

If the active root directory is tracked by a Git repository:

- **Status Probing:** Queries `git status --porcelain` before session start.
- **Git Checkpoint Tagging:** Optionally creates an ephemeral stash or commit tag: `refs/xcerpt/<sessionId>/pre-merge`.
- **Per-File Commit History Inspection:**
  - Right-clicking the file header allows developers to view recent Git commits on that file.
  - Developers can compare the LLM's proposed changes not only to the current disk state, but to previous commits directly in Monaco Diff.
- **Post-Session Commit:** When all file actions are merged, a button offers: `[Create Git Commit]`, prompting for a commit message pre-populated with the LLM's Architectural Intent summary.

## 7. Operational User Journey (The Complete Workflow)

1. **Staging Context:** The developer curates their workspace context in Xcerpt v1.6 (with True-Size preview and in-line Code Generation Protocol).
2. **Prompting the LLM:** The developer drops the package into their LLM.
3. **Creating the Session:** The LLM responds with a batch packet. The developer presses `Ctrl+Shift+N` in Xcerpt and pastes the raw markdown.
4. **Automatic Triage:** The parser generates the Dev Session, creates a checkpoint, and displays the File Action checklist.
5. **Human Arbiter Review:**
   - Reviewer reads the Architectural Intent drawer.
   - Reviewer steps through files in the side-by-side Monaco diff.
   - Reviewer verifies skip blocks, accepts individual hunks, or accepts entire files.
6. **Completion:** When all actions are complete, Xcerpt offers to create a clean Git commit. The developer returns to Context Staging or initiates another parallel Dev Session.
